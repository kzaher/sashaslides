## 2. Evaluating the proposed hybrid (wasm kernel + wasm Node + x86-64 user-mode layer)

**What exists:** two proof-of-concept NOMMU wasm kernels (busybox shell level), interpreter-grade JS engines in wasm, and one x86-64 *system* JIT in wasm (QEMU-wasm). **What is missing — and it's the whole hard part:** a user-mode x86-64 DBT in wasm. CheerpX is 32-bit and closed, qemu-wasm has no linux-user build, Box64/qemu-user have no wasm ports, ax/unicorn are interpreters. So the hybrid does not save us from writing the x86-64 JIT we are already writing.

**The wasm kernel is a poor host for x86-64 guests.** Both WasmLinux and linux-wasm are NOMMU: no `fork`, no `mmap`/`mprotect` semantics, no async signal delivery, no code patching, one shared address space, no preemption (linux-wasm needs a Worker per task). Our guests need exactly the things they lack: Bun/JSC and V8 `mmap(PROT_EXEC)`+`mprotect` W^X flips and emit self-modifying code; Claude Code/Codex `fork/exec` shells and tools; Bun uses `clone`/futex threads; signals for job control. A user-mode DBT would still need its own guest address-space model, page tracking, SMC invalidation, futex/thread mapping and signal delivery — at which point the wasm kernel gives you only VFS/net/pipes/procfs, i.e. the easy 20% that CheerpX and gVisor-style layers just implement directly. Meanwhile it costs you kernel stability (both projects crash), a syscall-ABI shim (x86-64 struct layouts vs. wasm32 kernel — you'd need wasm64_nommu, which is even less proven), and Worker-per-task/SAB threading constraints. Wasm still has no MMU/mprotect (memory-control proposal is not shipped); JSPI/stack-switching (Chrome 137+) helps blocking syscalls but not memory protection.

**"Node compiled to wasm" doesn't help either.** Node-WASIX proved V8-in-wasm runs only as an interpreter (Wasmer abandoned it); Bun cannot be built for wasm; and Claude Code is a Bun-compiled binary embedding its own runtime, so a wasm Node wouldn't run it. Codex is a Rust binary (open source, could be recompiled to wasm32-wasi in principle) and agy is a Go binary (PCLMUL, closed) — recompilation is not uniform. If a JS-package distribution of Claude Code exists, running it on the browser's *native* V8 (WebContainers-style) is by far the fastest path and needs no kernel-in-wasm at all.

**Effort:** realistically 1–2 engineer-years to make either wasm kernel robust enough plus a syscall-ABI shim, *on top of* the x86-64 DBT — versus zero kernel work if the DBT talks to a purpose-built syscall layer (CheerpX model) or to the existing emulated real kernel.

## 3. Performance expectations

- **Full-system interpretation (Bochs, current):** ~30–100× slower than native; ktock's pigz-10 MB benchmark: Bochs ≈ 40 s vs QEMU-wasm TCG ≈ 13 s (1 thread) / ≈ 7.5 s (4-thread MTTCG) — Chrome 130, i7-10510U ([FOSDEM slides](https://archive.fosdem.org/2025/events/attachments/fosdem-2025-6290-running-qemu-inside-browser/slides/238760/slides_1dDtpcS.pdf)). Boot 10–50 s because a real kernel boots under interpretation.
- **User-mode / system DBT to wasm (QEMU-TCG-wasm, CheerpX):** 3–6× over Bochs today; CheerpX reports 5–10× slower than native, 2–3× for optimized code, with per-TB `WebAssembly.Module` compile latency and browser module-count limits as the main constraints. User-mode skips kernel boot entirely (start-up = program load).
- **Native wasm recompilation (WasmLinux/linux-wasm userland, elfconv):** near-native (elfconv 56–96%), but requires source or an AOT lifter, and gains nothing for JIT-heavy runtimes (V8/JSC fall back to interpreter mode).

## 4. Verdict and recommendation

**Not worth it.** WasmLinux and linux-wasm are pre-alpha NOMMU kernels whose value proposition (native-speed *recompiled* userland) is orthogonal to our need (running *unmodified* x86-64 AVX2 binaries with JITs inside). Bolting an x86-64 user-mode layer onto them means writing the same DBT anyway plus adopting a kernel that lacks fork/mmap/signals/preemption and is less stable than the guest kernel we already emulate.

Recommended path:
1. Keep building the native-wasm-EH + trace-JIT engine; use QEMU-wasm's TCG backend (TB→module, hot-threshold, MTTCG, 64-bit IR) as the reference for what browsers tolerate, and target ≥3–5× over Bochs as the first milestone.
2. Attack boot latency separately: snapshot/wizer-style pre-booted guest state (both linux-wasm and container2wasm point to snapshots as the big win) — this removes most of the 10–50 s without any architecture change.
3. Longer-term, if start-up must approach zero, evolve toward a **CheerpX-style user-mode x86-64 DBT with our own Linux-syscall layer in JS/wasm** (no guest kernel), rather than a wasm-compiled kernel — that is the only architecture that gives both no-boot start-up and full mmap/SMC/fork control. Watch CheerpX 64-bit (announced as future work) as a possible commercial shortcut, and elfconv x86-64 as an AOT option for the non-JIT binaries (Codex, agy).

## Hybrid: wasm-native Node and Python, interpret only some x86-64 binaries

**Premise check first.** WasmLinux and linux-wasm run wasm processes compiled against *their* patched musl and their own kernel-entry ABI — not WASI, not Emscripten, not WASIX. So none of the existing wasm builds below run inside them as-is; every runtime you want on the "wasm side" is a re-port to a third, unstable ABI, and every dynamically-loaded C extension has to be relinked `-fPIC/-shared` for a NOMMU loader ([WasmLinux](https://github.com/okuoku/wasmlinux-project), [linux-wasm](https://joelseverin.github.io/linux-wasm/)).

**1. Python in wasm.** CPython treats `wasm32-wasi` as tier 2 since 3.13 (WASI 0.1, WASI-SDK 24 for 3.13/3.14; [PEP 816](https://peps.python.org/pep-0816/), [tier-2 announcement](https://discuss.python.org/t/wasi-has-been-promoted-to-a-tier-2-platform/45525)); Emscripten was dropped to unsupported in 3.13 and re-promoted to tier 3 in 3.14 ([discussion](https://discuss.python.org/t/wasm32-emscripten-and-wasm32-wasi-have-been-promoted-to-tier-3-platforms-for-cpython/17590)). Limits: **no threads, no subprocess, no sockets in WASI 0.1** — the test suite fails on exactly those ([Tools/wasm/README](https://fossies.org/linux/Python/Tools/wasm/README.md)); pip/C-extensions require rebuilding per ABI. Pyodide (Emscripten) is the mature browser build with ~250 prebuilt packages, but "does not support fork and pthreads; threading, multiprocessing, subprocess raise RuntimeError" and is **3–5× slower than native** ([FAQ](https://pyodide.org/en/stable/usage/faq.html), [constraints](https://pyodide.org/en/stable/usage/wasm-constraints.html)). MicroPython/RustPython are lighter but not drop-in for real tools. Net: Python-in-wasm is real but process-model-poor; nothing on our binary list needs it.

**2. Node in wasm, options for a mixed userland.**
- *Compiled Node:* Node-WASIX proved V8 can be built for wasm, but "V8 is running in interpreter mode inside of Wasm" and Wasmer abandoned it for native-engine Edge.js (Mar 2026) ([Wasmer](https://wasmer.io/posts/edgejs-safe-nodejs-using-wasm-sandbox)); wasix-org still shows no maintained node build ([wasix-org](https://github.com/wasix-org)). Leaning Tech's BrowserPod (2026, commercial, $0.01/h) claims "Node.js v22 … that source, compiled to a new target" with millisecond boots, but doesn't disclose the engine tier ([compare](https://browserpod.io/compare/browserpod-vs-webcontainers/), [site](https://browserpod.io/)). JSC.js is an LLInt-only JSC (~4 MB, no JIT) ([JSC.js](https://github.com/mbbill/JSC.js)); QuickJS-wasm is small and fast to start but a pure interpreter ([quickjs-wasi](https://github.com/vercel-labs/quickjs-wasi)). Bun has no wasm target (Zig runtime + mimalloc/uSockets/BoringSSL/io_uring).
- *Native-host Node (WebContainers style):* StackBlitz "reproduces the Node.js API on the browser's own V8" with a wasm VFS, process table and ServiceWorker network stack ([WebContainers](https://blog.stackblitz.com/posts/introducing-webcontainers/)) — that is the only near-native JS path in a browser, and it is precisely "a host JS process pretending to be a guest process": Node's `fs`/`net`/`child_process` calls are re-routed to a JS/wasm kernel-ish layer. Prior art for bridging that into a *Linux* kernel: WebContainers itself (closed), Emscripten's `FS`/`PROXYFS` and QEMU-wasm's 9p `-virtfs` bridge to Emscripten FS ([FOSDEM slides](https://archive.fosdem.org/2025/events/attachments/fosdem-2025-6290-running-qemu-inside-browser/slides/238760/slides_1dDtpcS.pdf)), and SGX-LKL, where a musl shim redirects syscalls into an in-process LKL ([SGX-LKL](https://arxiv.org/pdf/1908.11143)). So it is doable — a `libc`-level shim in the host JS that forwards `open/read/pipe/socket/waitpid` to LKL's syscall entrypoint via SAB+Atomics — but it exists nowhere today, and it doesn't help Claude Code's Bun binary at all.

**3. Mixed-ABI process model.** `exec()` dispatch is the easy part: `binfmt_misc`-style sniffing (`\0asm` → instantiate a wasm module in a fresh Worker; ELF64/x86-64 → hand to the DBT), and pipes/fds/signals/`waitpid` are naturally shared once *both* sides call the same kernel entrypoint — that is the one genuine benefit of a shared kernel: one VFS, one pid table, one socket layer, `bash | grep | node` just works. Everything else cuts against it. The x86-64 side needs a user-mode DBT with full Linux syscall translation (struct-layout conversion x86-64→wasm32 kernel, or use `wasm64_nommu`), a guest address space with page-granular tracking, `mmap/mprotect/W^X` and SMC invalidation for JSC/V8, `clone`+futex→Workers, and *asynchronous signal delivery* — but both wasm kernels lack `fork`, `mmap`, preemption and async signals ([linux-wasm](https://joelseverin.github.io/linux-wasm/), [WasmLinux demo notes](https://wasmlinux-demo.pages.dev/)). There is **no prior art** of user-mode emulation inside WasmLinux/linux-wasm/LKL-wasm; the closest are Qiling (Unicorn + its own syscall handlers, no LKL) ([Qiling](https://qiling.io/comparison/)) and QEMU-wasm, which lists user-mode as future work. And because wasm processes and x86-64 processes have different memory models (shared SAB vs DBT-managed guest RAM), `fork` remains impossible for wasm processes and merely hard for x86-64 ones — Claude Code and Codex spawn shells constantly. A VFS-only glue between two worlds (host-V8 Node + our x86-64 machine sharing 9p/pipes) gets ~80 % of the benefit with none of the kernel rewrite.

**4. Our binaries.** *Claude Code*: the native install is a Bun single binary (JSC + Zig runtime, AVX2) → **must stay x86-64**; the deprecated-but-published npm `cli.js` runs on Node ≥18 ([npm](https://www.npmjs.com/package/@anthropic-ai/claude-code), [install guide](https://www.nxcode.io/resources/news/install-claude-code-setup-guide-2026)) and is the only thing that could run on host V8 — but that path needs no wasm kernel, just a WebContainers-like shim, and it is a moving/deprecated target. *Codex*: Rust, source available; `wasm32-wasip2` is plausible for the core, but tokio/reqwest+rustls, `child_process` spawning, landlock sandboxing and the TUI need WASIX-class syscalls and yet another ABI port — weeks-to-months of upstream-divergent work with no maintenance guarantee. *agy*: closed-source Go binary, PCLMUL → **x86-64 only** ([StackNova](https://stacknovahq.com/ai-tools-for-developers/antigravity-cli-tested-real-project)). So 2 of 3 flagship binaries stay on the emulated side regardless, and the third gains nothing from a wasm kernel.

**Verdict unchanged — not worth it.** Effort: wasm kernel hardening (both are crashing PoCs, last WasmLinux commit Oct 2024) + third-ABI ports of Node/Python/Codex + a from-scratch x86-64 user-mode DBT with SMC/mmap/signals + a mixed-ABI process layer ≈ 2–3 engineer-years, and the payoff lands only on binaries that don't drive our product. Benefit vs. current path (Bochs full-system + trace JIT, ~10 s boot): the JIT rebuild already targets the 3–6× that DBT gives over Bochs ([FOSDEM pigz numbers](https://archive.fosdem.org/2025/events/attachments/fosdem-2025-6290-running-qemu-inside-browser/slides/238760/slides_1dDtpcS.pdf)); boot time is better attacked with pre-booted snapshots. If you want a "wasm-native fast lane" cheaply, do it *outside* the guest: run Node-based tools on host V8 with a WebContainers-style shim, and share files with the emulated machine over 9p/virtio-fs — no shared kernel needed.
