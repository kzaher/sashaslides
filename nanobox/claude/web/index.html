nanobox/claude — original vs optimized VM

Each page boots the same container image on two engines at the same time: the original container2wasm WASI engine (Bochs) on top and the optimized engine below (the same Bochs memory model, rebuilt with native wasm exception handling and a trace JIT that compiles hot x86-64 code to WebAssembly). Under each VM a timer counts until that CLI's sign-in screen is on the terminal — that time is the result.

  • claude — Claude Code (Bun-compiled; needs AVX2)
  • codex — OpenAI Codex (Rust)
  • agy — Antigravity CLI (Go; needs PCLMUL)
  • claude-npm — Claude Code 2.1.112 installed with npm install -g on system Node.js 22 (emulated, optimized engine; 84.4 s, 7.8 G instructions — build-claude-npm.sh)
  • claude-native — the same cli.js run directly on this browser's V8 in a Web Worker, no emulation (sign-in in ~1.0–1.3 s with the in-memory rootfs; ?backend=vm = files/tty/child processes in the emulated guest through the nbnode shim, ~4.0–4.3 s; a separate track without memory identity — docs/claude-native.md)

Sandbox: Linux only from us, everything else from the vendors (no memory identity)

We serve a 3.9 MB Linux rootfs + the engine (29.8 MB slim) + optional kernel JIT bundle; on first visit a JavaScript installer fetches node (npm registry), npm, claude (npm, 2.1.112 = last release on system node), codex (npm) directly from the vendors with sha512 checks and agy (Google) through the relay; everything lands in a persistent, browser-filesystem-backed /usr/local, /root, /home, /var shared by all pages of this origin (second visit: zero downloads). Claude Code runs on the browser's V8 (its node in the guest is the shim), codex/agy run natively in the guest:

  • sandbox.html?cli=claude — cold 5.5 s (install 73 MB in 1.6 s) · warm 4.8 s
  • sandbox.html?cli=codex — cold 11.3 s (177 MB) · warm 8.0 s
  • sandbox.html?cli=agy — cold 22.5 s (110 MB) · warm 20.3 s

Cross-origin traffic: through the open-source proxy extension when installed (0 relay hits), else our relay only for the vendors that don't answer CORS (web/netpolicy.js, enforced server-side), else direct browser fetch. Details: docs/sandbox.md.

claude on system node — two more pages (no memory identity)

Claude Code installed the official way (npm install -g @anthropic-ai/claude-code, system Node.js 22 — the npm package runs cli.js on whatever node is on PATH; the "native" installer/original image instead ships its own packed Bun runtime, which is what claude.html emulates):

  • claude-native.html?backend=vm — system node = the browser's V8: the guest's node is a shim; Claude Code's JS runs on the page's V8, every file/tty/child-process call is executed inside the real Linux guest over /dev/hvc1. Sign-in in ~4.0 s (VM boot 0.9 s + shim hello 2.1 s + run 1.6 s).
  • claude-native.html — same JS on the browser's V8 with an in-memory rootfs (no VM at all): ~1.0–1.3 s.
  • vm.html?engine=opt&image=claude-npm — the same image fully emulated (system node's V8 as x86 under the trace JIT): 84 s — node's flat, self-modifying V8 code is a worse fit for the trace JIT than Bun's one GC loop.

the sandbox — Linux-only image, first-run installer, persistent tree (docs/sandbox.md)

The image is busybox + glibc (3.9 MB, linux-base). On the first visit an installer running on this browser's V8 fetches node 22 + npm and the CLI from the vendors' servers (npm registry / Google; sha512-verified) into ONE persistent tree (OPFS, shared by every page on this origin) that the VM mounts over /usr/local /root /home /var; the guest's writes (~/.claude.json, ~/.codex, …) are journaled back. The second visit downloads nothing.

  • sandbox.html?cli=claude — Claude Code 2.1.112 (npm) on this browser's V8 behind the guest shim: 5.5 s cold / 4.8 s warm to sign-in
  • sandbox.html?cli=codex — Codex 0.147.0 (npm platform binary, runs in the guest): 11.3 s cold / 8.0 s warm
  • sandbox.html?cli=agy — Antigravity CLI 1.1.13 (Google's tarball, relayed): 22.5 s cold / 20.3 s warm
  • sandbox.html?cli=sh — a busybox shell in the guest with the persistent tree mounted (?install=… chooses what is mounted; ?reset=1 wipes the tree)

What the optimized engine is

The same Bochs machine model as the original (same devices, BIOS, kernel, rootfs, instruction-count driven clock — that is what keeps guest memory byte-identical: test/identity.sh boots codex/agy to the sign-in screen on the reference and the optimized engine under a deterministic harness and compares ticks + SHA-256 of all guest RAM), rebuilt with wasi-sdk 33 and native WebAssembly exception handling instead of Asyncify, plus a trace JIT that compiles hot x86-64 traces to small wasm modules with Bochs' exact chaining/interrupt semantics. In the browser the bigger lever is the runtime: the container rootfs is unpacked in the VM worker and served through the built-in virtio-9p as a WASI preopen instead of guest-TCP → network-stack worker → 9p server.

Compare-page runs = both engines booted at the same moment on one page (test/e2e.mjs, results/*.json), optimized engine with regions + JIT 2:2000 + pre-computed bundles (kernel + image). The memory-identity check (reference vs optimized engine, RAM SHA-256 at the sign-in screen) is test/identity.sh: identical for codex and agy.

The original engine's sign-in time is memoized per image (results/<image>-orig.json, refreshed by node test/e2e.mjs <image> --engine orig --record): the compare pages boot only the optimized engine — the thing under test — and show the recorded original time. ?orig=live (codex, agy, claude) boots both side by side for a live comparison (1–5 minutes).

Options: ?jit=2:2000 (JIT level:threshold for the optimized engine, jit=0 = same build interpreted), ?cmd=…. Single VM: vm.html?engine=orig|opt&image=codex. Both frames share one CPU budget; a laptop with a few cores runs them side by side without starving either.
