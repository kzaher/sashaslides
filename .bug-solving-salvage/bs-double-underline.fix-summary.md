On slide_09 the active nav-link (`.nav-link.active { border-bottom: 2px solid #6366f1 }`, an inline `<span>`) rendered with two nearly-coincident underlines: `emitRect(el, style, bounds)` painted the element's `border-bottom` as a bordered rect, while the text path independently synthesized a native `textDecoration:'underline'` for the same inline-border-underline case — the two paths were uncoordinated because `inlineBorderUnderline` was computed *below* the `emitRect` call, so the rect emit had no way to know the bottom border was about to be re-expressed as a native underline. The fix, in `renderer/html2slides/extract-dom.ts`, hoists the `inlineBorderUnderline` detection to just above the rect emit (`extract-dom.ts:2638`) and, when true, hands `emitRect` a stripped style (`extract-dom.ts:2642-2658`) with `borderBottom:0`, `borderBottomColor:null`, `borderSides.bottom={width:0,color:null,style:'none'}`, and the uniform `borderWidth`/`borderColor` convenience fields recomputed from the remaining sides — which collapse to `0`/`null` for an underline-only element so `emitRect`'s `hasBorder` gate is false and no border rect is emitted (`extract-dom.ts:2659`). The text block below now reuses that same hoisted boolean instead of recomputing its own (`extract-dom.ts:2842-2845`, feeding the unchanged `borderAdjust` and the `textDecoration:'underline'` at `extract-dom.ts:2982`), so the two sites can no longer diverge. The gate requires an inline tag (`a`/`span`/`inline-block`) with ONLY a border-bottom and no background, so block dividers and bordered boxes are untouched; the result is a single native underline under "Home" instead of a painted border rect stacked beneath the text underline.
