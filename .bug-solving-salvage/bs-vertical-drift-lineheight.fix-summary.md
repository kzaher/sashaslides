# Vertical-drift / line-height — fix summary

Root cause: the DOM-extraction step gated only on `document.fonts.ready`, which can resolve BEFORE a `fonts.googleapis.com` `@font-face` stylesheet has actually registered its faces. Extraction therefore measured FALLBACK-font metrics (line boxes ~1px shorter than the real webfont), so every text block's computed height came out slightly short and the accumulated deficit shifted content upward — exactly the user's "everything moved up, worse toward the bottom" report across slides 03/06/25/26/29/32 (the initial half-leading `spcPct` hypothesis in `analysis.md` was superseded once the real cause proved to be extraction-time font metrics, not the emit-time line-spacing model). The fix replaces the weak `document.fonts.ready` + fixed-sleep gate in `renderer/html2slides/convert-pptx-io.ts:107-128` with a robust font-readiness sequence: wait for every `link[rel=stylesheet]` to load (with a 3s cap), force-load every declared `document.fonts` face, await `document.fonts.ready`, then poll `document.fonts.check()` for every font-family actually used on the page (2s deadline) before running the extractor — guaranteeing real webfont metrics are measured. Two adjacent converter fixes rode in on the same commit (`renderer/html2slides/convert-pptx-lib.ts:335-339`, propagating CSS `letter-spacing` → run `charSpacing` on the styled-runs path; and `convert-pptx-lib.ts:2176-2179`, reviving colored literal-glyph `::before` bullets on `list-style:none` lists), but the webfont-readiness gate is the change that resolves the vertical-drift cluster. Slides 10 and 33 were mis-clustered (shape/SVG-stroke defects, not text drift) and are unaffected by this fix.
