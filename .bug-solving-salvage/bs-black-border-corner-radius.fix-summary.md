The slide_12 device mockup rendered with the wrong background corner radius and spurious oversized black borders because the file-write convert path had silently stopped applying three of its OOXML zip post-patches. The product/sidebar path (`buildPptxInMemory`, `convert-pptx-lib.ts:3506-3527`) still post-patched the stock-pptxgenjs output, but the regen/convert-pptx and bug-solving `before`-recorder path (`runConvertPptx` in `renderer/html2slides/convert-pptx-io.ts`) only called `injectGradients` and `injectStrokeAlignment` (`convert-pptx-io.ts:375-376`) after the type-safety refactor, and a stale comment (`convert-pptx-io.ts:397-404`) wrongly claimed "all OOXML fixes are now NATIVE … no zip post-patches remain." As a result the `.screen` `round2SameRect` shape emitted a single bare `<a:gd name="adj">` — which OOXML/Google Slides does not recognise for that preset, so it fell back to the preset default radius on both handle pairs (the "wrong background radius", visually read as an upside-down/rotated gradient) — and ~43 shapes that requested no stroke emitted an empty `<a:ln>` that Google imported as a default ~1pt stroke (the "black borders too big"). The gradient direction, `flipV`, and group structure were already identical to the last user-rated-good pptx, so this was a pure wiring regression, not geometry/gradient math. Fix: after the existing `injectStrokeAlignment` call I restored the three dropped file-based wrappers — `injectRound2SameRectAdj` (adj1=11429/adj2=0 handle naming → correct corner radius), `injectShapeNoLine` (empty `<a:ln>` → `<a:ln><a:noFill/></a:ln>` → removes the default strokes), and `injectCellNoBorder` (table-cell no-border parity) — at `convert-pptx-io.ts:377-384`, and corrected the misleading "no zip post-patches remain" comment to accurately reflect that only shape groups are native on this path (`convert-pptx-io.ts:397-405`). No changes to gradient, `flipV`, or geometry code.
