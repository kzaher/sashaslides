# html2slides — Google Slides add-on

A Google Slides sidebar with the same UX as the standalone html2slides page:
**paste HTML (Ctrl+V) or pick `.html` files → it converts them locally and
inserts the slides right after the slide you're currently on.**

```
┌──────────── Slides editor ────────────┬─ sidebar ─┐
│                                        │  [drop /  │
│        (your presentation)             │   paste   │
│                                        │   HTML]   │
│                                        │  Insert ▸ │
└────────────────────────────────────────┴───────────┘
```

## How it works

1. The sidebar (`Sidebar.html`) is the html2slides browser bundle. It renders
   the input HTML in an offscreen 1280×720 iframe, extracts geometry, and builds
   a `.pptx` **entirely client-side** (pptxgenjs + jszip are inlined). No file
   ever leaves your machine except the finished pptx bytes.
2. It base64-encodes the pptx and calls `google.script.run.insertPptxAfterCurrent`.
3. `Code.gs` converts the pptx → a **temporary** Google Slides file via the
   Advanced Drive Service (same importer as *File → Import slides*, so fidelity
   matches what you get today), copies each slide into the active deck **after
   the current slide** with `Presentation.insertSlide(index, slide)`, then
   deletes the temp file.

## Build

```bash
npm run build:addon   # or: npx tsx renderer/html2slides/browser/build-addon.ts
# → dist/renderer/html2slides/addon/{appsscript.json, Code.gs, Sidebar.html}
```

The output dir is autogenerated (gitignored) — edit the sources, not the output:
- UI / client flow → `browser/addon-main.ts`
- shared conversion → `browser/convert-core.ts` (also used by the standalone page)
- server + manifest → string templates in `browser/build-addon.ts`

## Deploy (Tier 1 — bound script, just you, ~5 min)

This is the fastest way to try the end-user flow. No publishing, no review.

**Option A — manual paste (no tooling):**
1. Open any Google Slides presentation → **Extensions → Apps Script**.
2. **Project Settings (gear) → tick "Show appsscript.json manifest file"**.
3. Replace `appsscript.json` with `dist/renderer/html2slides/addon/appsscript.json`.
4. Replace `Code.gs` with `dist/renderer/html2slides/addon/Code.gs`.
5. **File → New → HTML file**, name it `Sidebar` (no extension), paste
   `dist/renderer/html2slides/addon/Sidebar.html`.
6. Save. Reload the presentation. You'll get an **Extensions → html2slides →
   Open html2slides** menu item → click it → grant permissions (first run shows
   the "unverified app" warning — *Advanced → Go to … (unsafe)*) → the sidebar
   opens.

**Option B — clasp (push the whole project):**
```bash
npm i -g @google/clasp
clasp login
cd dist/renderer/html2slides/addon
# bind to a specific presentation (get its id from the /d/<ID>/edit URL):
clasp create --type slides --title "html2slides" --parentId <PRESENTATION_ID>
clasp push
```
Then reload that presentation and use **Extensions → html2slides**.

> The first time, also enable the **Drive API** advanced service if Apps Script
> prompts (the manifest already declares it, so usually it's automatic).

## End-user UX recap

- **Turn on:** install once (paste or clasp); thereafter it lives under the
  **Extensions** menu of that presentation.
- **Use each session:** Extensions → html2slides → Open → sidebar appears →
  paste/drop HTML → **Insert after current slide**.
- Editor add-on sidebars can't auto-open on document load — they're opened from
  the menu. (An auto-showing right-rail panel would require the CardService
  "Workspace Add-on" model, which can't host this custom HTML UI.)

## Promote to more users (Tier 2/3)

- **A few known testers:** wrap as an Editor Add-on in a GCP project, keep it in
  *Testing*, add their emails as test users. They install via link, click
  through the unverified warning, done.
- **Public / clean one-click install:** publish to the Google Workspace
  Marketplace — requires Google's OAuth verification (privacy policy, demo,
  review) because Slides + Drive are sensitive scopes.

## CSP / eval handling (built in)

The sidebar renders the input HTML in an offscreen iframe and runs the
extractor inside it. Apps Script serves the sidebar from a sandboxed
`googleusercontent.com` iframe, so `convert-core.ts` tries two mechanisms and
uses whichever the host CSP permits:

1. **`iframe.contentWindow.eval(blob)`** — primary; the extractor's return value
   is the JSON. Works on the standalone page and any normal browser.
2. **Inline `<script>` injection** — fallback when `eval` is blocked
   (`unsafe-eval` absent). The extractor also stashes its result on
   `window.__H2S_EXTRACT__` (a harmless side effect added to `extract-dom.ts`),
   which the injected-script path reads since it has no completion value.

If a host somehow forbids *both* `eval` and inline scripts, extraction throws a
clear error in the sidebar log naming the cause. In practice Apps Script allows
at least one (our whole bundle is itself an inline `<script>`, so inline runs).

## Fidelity / limits

- `insertSlide(index, slide)` copies layout/text/images well. Charts linked to
  Sheets or embedded videos may need relinking; copying many slides can
  duplicate masters/layouts. For html2slides decks (static shapes/text/images)
  this is a non-issue.
- Large decks: the base64 round-trip and the Drive conversion are subject to
  per-user Drive/Slides quotas — fine interactively.
